# 编码规范指南

## 前言

- 项目支持 C++ 23，不支持 Module。
- 下面指南适用于 APP、BSP、MODULE、Algorithm 目录内的代码文件。
- 下面指南不适用于移植的第三方库。对于这些库，不做侵入式的改动。

## 类型、变量、宏

- 声明结构体不要使用 `typedef`。
- 减少使用宏。
  - 对于仅用于局部实现的宏，在最后一次使用后及时 `#undef`；头文件应尽量避免暴露不必要的宏。
  - 注意宏展开时的多次求值问题。
- 减少使用可变的全局变量。

## 控制流与表达式

- 计算与条件判断应尽可能无副作用，避免混合状态修改与结果计算，或依赖求值顺序执行操作。
- 优先使用 `if-else if-else` 表达同级互斥条件，避免不必要的嵌套。
- 优先使用卫语句处理异常或边界情况，减少嵌套层级。
- 避免复杂的布尔表达式，不应为了减少嵌套而牺牲可读性。
- 三元运算符仅用于简单的二选一取值，禁止嵌套，避免副作用。

## 内存与对象生命周期

- 明确对象实例存在哪里、何时创建、何时销毁。
  - 注意某些类的实例必须具有静态存储期才能工作。
- 优先保证零堆分配。
- 需要容器时，优先使用数组，或者零堆分配的链表。
  - `std::vector`、`std::string`、`std::function` 等类型可能触发动态内存分配，需要结合实现和使用方式评估。
优先保证零堆分配。
- 返回局部变量时通常直接使用 `return value;`，避免无必要的 `return std::move(value);`。

## 函数与返回值

- 一个函数尽量只完成一项明确的工作，函数名要清晰表达函数做的所有事情。
  - 如果函数名过长，考虑是不是函数做了太多工作。
- 函数需要接收大体积对象时，关于用引用还是指针，应考虑是否存在“空”的状态。
  - 如果存在空的状态，考虑指针，并且处理空指针的情况。
  - 如果是必须存在的对象，考虑引用。
- 对于用来获取值的函数（getter），使用 `[[nodiscard]]` 提醒调用者要接住返回值。
  - 只是返回错误值、状态码的函数，不使用这个属性标注。
- 返回的结果可能为空时适合考虑 `std::optional`，需要保留错误原因时适合考虑 `std::expected`。
  - 某些情况下，调用方只需要知道操作是否成功，而不关心原因，这时候用 `bool` 返回就足够了，不必为此新增一些错误类型枚举。

## 类与资源管理

- 当发现某些逻辑反复使用、可能存在多个实体、状态和行为有关联、可能需要模块化的情况，考虑设计成类。
- 默认遵循零法则。
  - 只有在确实需要时，比如拥有一些裸指针，才手动实现析构、拷贝和移动操作。
- 如果某个类不是由你维护的，那就不要轻易改动这个类的成员的可见性。

## 并发与中断

- 考虑清楚代码跑在什么环境，是 RTOS 任务上下文还是中断上下文，或者 RTOS 内核启动前。
- `volatile` 不等于原子操作，也不能代替互斥锁或内存序同步。
  - 必要时，考虑使用原子变量。
- 进入临界区的范围尽量小，并保证所有退出路径都能正确恢复中断状态。
- 中断函数内不应该做耗时操作。

## 错误处理与断言

- 对可预期的运行失败，使用返回值、状态码或明确的错误类型，并且做好对应的错误处理。
- 能使用编译期检查的约束，优先使用 `static_assert`、类型特征和合适的 `concept`。
- 对于无法在编译期验证、但能在初始化或运行时检查的配置约束，考虑使用运行时断言检查。
  - 例如，CubeMX 中对外设的配置。
- 不要直接调用 `Error_Handler`，应使用 `RUNTIME_ASSERT`，后者能记录断言失败的位置（`Asserter` 会记录），以便调试。
- 不写重复冗余的检查。
- 不要滥用运行时断言。
  - 应当优先保证稳定运行。
  - 如果一些错误，无法在程序中自己修复，并且不修复会严重影响运行、甚至崩溃时，才考虑使用运行时断言。

## 头文件与模块组织

- `APP` 可以依赖 `BSP` 和 `MODULE`。
- `BSP`、`MODULE` **不应该**反向依赖 `APP`。
- 由于 HAL 库神秘的头文件顺序问题，建议直接引用 `main.h`。
  - 语言服务器有时会自动补全像 `stm32h7xx.h` 之类的头文件引用，有 `main.h` 的情况可以考虑删掉。
  - 尽管这不太规范，但有时候确实省事。
- 头文件优先使用 `#pragma once` 而非 `#ifndef`、`#define`、`#endif` 组合。

## 注释

- 使用简体中文注释。
- 函数使用 Doxygen 风格中文注释。
  - 公开接口应该有这样的注释。
  - 注释不必覆盖所有函数、变量。
  - 连续长段的逻辑，可以在段前用一句话注释，说明此段代码在做什么。
- 注释应该和代码一致，不要只改一个忘记改另一个。

## 命名

统一使用有明确含义的名称，避免不必要的缩写。

| 对象                  | 命名风格           | 示例                               |
| --------------------- | ------------------ | ---------------------------------- |
| 类、结构体、枚举类型  | 大写驼峰           | `UartPort`、`MotorState`           |
| 函数/成员函数（方法） | 小写蛇形           | `read_sensor()`                    |
| 全局变量              | `g_`前缀、小写蛇形 | `g_initialized`                    |
| 成员变量（属性）      | `m_`前缀、小写蛇形 | `m_size`                           |
| 常量、编译期常量      | `k`前缀、大写驼峰  | `kBufferSize`                      |
| 模板参数              | 大写驼峰           | `template <std::size_t QueueSize>` |
| 命名空间              | 小写蛇形           | `namespace motor_control`          |
| 宏                    | 大写蛇形           | `STM32_USE_DMA`                    |

- 大写驼峰遇到缩写时，也应该保证首字母大写，其余字母小写。
  - 例如，应该是 `UserId` 而不是 `UserID`。
- `k` 前缀只用于开发者显式定义、具有独立名称的常量，而不用于元编程中的模板参数、类型特征等编译期实体。
- 结构体成员不必使用 `m_` 前缀。

## 缩进与空格

- 使用 4 个空格缩进，不使用 Tab。
- 左花括号与语句同行。
- 运算符两侧留空格，逗号后留空格。

## 工具与工程检查

- 合并/烧录代码前，务必检查各调试功能的开关。不要将调试代码合并到主分支。
- 编译器警告是否得到处理，是否存在未初始化变量和类型转换问题。
- 是否存在越界访问、悬空引用、数据竞争和生命周期错误。
- 是否涉及堆分配。
- 修改是否影响现有模块接口和其他调用方。
